There's a habit some engineers have of conflating commit size with change size. They write small commits, but each commit is one piece of a large undivided change that only makes sense as a whole. The commits are atomic in the git sense; the work is not.

The distinction matters because reviewability is about comprehension, not line counts. A 400-line diff that changes one thing cleanly is easier to review than four 100-line diffs that are each a quarter of something you can't evaluate yet.

The test I use: could this commit be reverted independently without breaking something? If no, it's not really a unit — it's a fragment. Fragments should either be combined or the work should be restructured so they stand alone.
