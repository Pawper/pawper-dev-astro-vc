TypeScript has a reputation problem on the backend. The reputation isn't entirely undeserved: if you've ever looked at a codebase where every API response is wrapped in three layers of generic types, each with its own namespace and a 60-line definition file, you understand why people call it verbose.

The thing is, that verbosity is a choice. TypeScript gives you the tools to be precise about your data — it doesn't require you to be exhausting about it.

## What type-safe APIs actually need

I've worked on APIs that were meticulously typed and APIs that weren't. The difference in maintenance experience isn't subtle. The core benefit isn't what most people describe — it's not catching typos in property names. It's that the types are live documentation.

When a new developer opens a route handler and the return type is explicitly declared, they know what that route produces. They don't have to trace through three middleware functions and a database query to figure out the shape of the response. The type is right there, it's correct by construction, and the compiler will tell them if they break it.

That's the goal: types that communicate intent, not types that demonstrate thoroughness.

## Start with your domain types

The mistake I made early with TypeScript APIs: I started by typing the framework layer and worked inward. Request objects, response wrappers, route parameter shapes. By the time I got to the business logic, I had a lot of types and very little confidence in them.

The right order is the reverse. Start with the domain. What are the core entities in the system? What do they look like at rest — in the database — and in flight — in API responses?

```ts
interface User {
  id: string;
  email: string;
  createdAt: Date;
}

interface UserResponse {
  id: string;
  email: string;
  createdAt: string; // serialized for JSON
}
```

These are simple. They're meant to be. When they're right, every other type in the system derives from them. The framework types become plumbing; the domain types become ground truth.

## Avoiding the wrapper trap

Here is a pattern I've seen in several codebases and try not to repeat:

```ts
type ApiResponse<T> = {
  data: T;
  error: null;
  meta: ResponseMeta;
} | {
  data: null;
  error: ApiError;
  meta: ResponseMeta;
};
```

This is technically fine. It's a discriminated union, it's type-safe, it models the reality of an API that can succeed or fail. But every consumer now has to unwrap the `data` field before using it, and every function that touches an API response has to import and understand this type.

The alternative: make your success and error cases explicit at the route level. Handle errors in middleware. Return domain types directly from route handlers. The consumer gets the shape they care about, not a generic wrapper.

This is a case where less type machinery produces more readable code. The types are still there; they're just not getting in the way.

## Zod for validation, types for everything else

Runtime validation is the one place where explicit validation libraries earn their keep. A TypeScript type tells the compiler what shape to expect; it cannot prevent a malformed request from arriving at runtime.

Zod (or a similar library) handles the boundary cleanly: define the schema once, infer the TypeScript type from it, validate incoming data against it. You don't write the type and the validator separately and hope they stay in sync — you write the schema and get both for free.

```ts
const CreateUserSchema = z.object({
  email: z.string().email(),
  password: z.string().min(8),
});

type CreateUserInput = z.infer<typeof CreateUserSchema>;
```

The type `CreateUserInput` is always correct by construction. When the schema changes, the type changes with it. That's the level of automation that makes TypeScript actually worth using on the backend.

## Keep the types close to the code

One pattern that consistently causes problems: a centralized `types.ts` file (or directory) that holds every type in the codebase.

The problem is discoverability. When types live far from the code that uses them, they stop being read regularly. They drift. Someone updates a database schema, forgets to update the type, and the type silently lies about the shape of the data for three months until someone hits a runtime error.

Types belong next to the code they describe. A route handler and its response type should be in the same file, or at most in an adjacent file in the same directory. The closer the type is to the code, the more likely it is to be updated when the code changes.

## The maintenance test

Here's how I evaluate whether a TypeScript API setup is actually working: can a developer who has never seen a route understand its contract by reading the handler?

Not by reading the docs. Not by running the server and inspecting a response. By reading the handler, which has typed inputs and a typed return, and understanding immediately what comes in and what goes out.

If the answer is yes, the types are doing their job. If the developer has to follow a chain of generic imports to understand what `T` resolves to, the types are getting in the way.

The goal of a typed API is to make the code more readable, not less. If you find yourself reaching for a type alias to explain a type alias, that's a sign to simplify rather than annotate.
