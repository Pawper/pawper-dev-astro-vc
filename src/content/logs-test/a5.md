The first year I taught middle school, I wrote my lesson plans for myself. Clear objectives, logical sequence, all the content I needed to cover. I'd look at them the morning of class and think: yes, this is right. Then I'd walk into the room and watch twelve-year-olds stare at me with polite blankness, and I'd realize I had written documentation for someone who already understood the material.

The lesson it took me two years to internalize: documentation is not a transcript of what you know. It's a map drawn for someone who doesn't know where they're going.

## The reader's model, not yours

Every teacher learns to think about prior knowledge — what a student already knows that you can build on. The practical version of this is: when you write an explanation, you're always writing it on top of a model in someone else's head. If you don't know what that model looks like, your explanation lands in the wrong place.

I see this constantly in technical documentation. A README that starts with architecture decisions assumes the reader knows why those decisions matter. A function docstring that describes implementation details assumes the reader is already thinking about implementation. Neither is wrong — but both skip the question of where the reader is starting from.

When I write documentation now, I try to answer it explicitly: what does someone need to already know to make use of this? If the answer is "a lot," that's a signal, not a given. Either the documentation needs more scaffolding, or the thing itself needs to be simpler.

## The curse of knowing

There's a well-documented cognitive phenomenon called the curse of knowledge — once you understand something, it's nearly impossible to remember what it felt like not to understand it. You literally cannot access the mental state of the person you're trying to explain to.

Teachers encounter this constantly and develop countermeasures. The most reliable one: watch someone try to follow your instructions. Don't coach them. Don't correct them in real time. Just watch, and write down the places where they go wrong.

The software equivalent is user testing, which most internal tooling never gets. The substitute I use: ask someone unfamiliar with the codebase to perform a task using only the documentation. The task doesn't have to be complex. Setting up a local dev environment is enough. The wrong turns they take will tell you more about where your documentation fails than any amount of self-review.

## Concrete over abstract

Here's a thing that's true in classrooms and in README files: concrete examples land before abstract explanations, every time.

You can explain what a function does in one precise sentence, and it will be understood by the person who already had a working mental model. The person who didn't will nod and not understand. Show them a before-and-after — here's the problem, here's how the function solves it — and the sentence suddenly makes sense.

I've changed how I order documentation because of this. Abstract first used to feel more rigorous. It no longer does. I lead with the example and follow with the explanation. The explanation is there for people who want to understand the mechanism; the example is there for people who want to know what to do.

## Comments that don't explain the obvious

There's a category of documentation that's worse than no documentation: the kind that states what is already visible in the code.

```js
// Increment the counter
counter++;
```

This is noise. It adds no information, it trains the reader to ignore comments, and it clutters the file. The programmer who wrote it was trying to be helpful. The result is the opposite.

What comments should do — the only thing they should do — is explain the *why* when the *why* is not obvious from the code. Why is this value hardcoded? Because the API breaks on other values and we haven't filed the bug yet. Why does this function take this particular argument shape? Because we had to match a legacy contract.

That's the same principle as good teaching. Don't repeat what's in the textbook. Use your time to explain the part the textbook doesn't.

## The standard I hold documentation to

The question I ask before I consider documentation done: could someone who has never seen this code use it correctly, and understand correctly what "correctly" means?

The first part is about completeness. The second is about framing — a lot of documentation tells you how to use something but not what success looks like. Failure modes, edge cases, known limitations. These are the parts most documentation skips because they're embarrassing to write. They're also the parts that would have saved me an afternoon three separate times this year.

Students who can explain back what they've learned have actually learned it. Documentation that accurately represents the hard parts — not just the happy path — was written by someone who actually understood what they built.
