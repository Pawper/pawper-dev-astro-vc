The refactor-versus-ship decision is usually framed as a quality question: is the code good enough to go? I've found it's more useful to frame it as a cost question: what does waiting cost, and who pays it?

If the current code works but is hard to extend, the cost of shipping it now is that future changes are slower. That's a real cost, paid gradually, mostly by you. If the feature is blocking users from doing something they need to do, the cost of waiting is immediate and paid by them.

Neither cost is automatically higher. But they're often weighed unevenly — engineers tend to overweight code quality costs because they feel them directly. The user's cost is easier to abstract away.
