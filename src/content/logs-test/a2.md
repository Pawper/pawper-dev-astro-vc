There's a version of this project where I picked a clean, tasteful design system — Inter, clean whites, generous whitespace, the standard vocabulary of contemporary web design. It would have looked professional. It would have been immediately readable. It also would have been indistinguishable from fifty other developer portfolios built this year.

Instead I looked at Star Trek.

## Why LCARS

LCARS — the Library Computer Access and Retrieval System — is the fictional UI from Star Trek: The Next Generation, designed by Michael Okuda in 1987. It's immediately recognizable: bold horizontal bars, colored rectangular panels, rounded terminals, monospaced typography with lots of uppercase labels.

What I find interesting about it as a design reference isn't the aesthetics — it's the attitude. LCARS communicates that the person using it is an expert. There's no onboarding, no tooltips explaining what each panel does. The interface assumes competence. It's organized for efficiency, not for approachability.

A portfolio for a software engineer is exactly the right context for that attitude. The audience is technical. They don't need things explained to them. They need to be able to navigate to what they want quickly and trust that the person who built the interface thought carefully about the structure.

## Translating the reference

The Codex doesn't look like a Star Trek screen. I've kept just enough to be evocative while stripping out everything that would make it read as costume rather than design.

What stayed: the thick horizontal bars at the corners of panels (the "LCARS bar" in the CSS), the rounded cutouts, the monospaced uppercase labels, and some of the vocabulary — CASE-FILE, LOG, INDEX. These elements are present enough that someone familiar with the reference will recognize it, but absent enough that someone unfamiliar won't feel excluded.

What went: the orange-and-black color palette, the boxy panel shapes, the bezel-heavy layout. The Codex uses a much more refined palette, real photography, and blur effects that weren't possible in 1987 and weren't part of the original design language.

## Implementing the corner arcs

The LCARS corner — a quarter circle cutout where a horizontal bar meets a vertical panel edge — is the most recognizable element of the aesthetic. Getting it right in CSS took longer than I expected.

The naive approach is `border-radius` on the container, but that creates a curved corner, not a cutout. What LCARS has is a negative space — the panel cuts away to reveal the background behind it.

The actual solution: each LCARS bar is a positioned element with its own background. The corner arc is a pseudo-element on the panel, positioned at the junction, with a `border-radius` on the opposite corner to create the curved cutout shape. The background of the pseudo-element matches the content behind it, creating the illusion of a hole.

This breaks if the background isn't a solid color — which, with a blurred photo backdrop, it isn't. I worked around it by using a CSS `radial-gradient` on the pseudo-element that samples the approximate tonal value of the background at that position. It's approximate, but at the scale these elements render, it reads correctly.

## The CSS variable architecture

Every colored LCARS element in the Codex inherits from a set of scoped CSS custom properties: `--section-accent`, `--section-deep`, `--section-rgb`. These are set at the section level and cascade down.

The practical effect: changing the accent color for a section — projects use blue, logs use green, the personnel section uses orange-red — requires changing one variable on a wrapper element. Every child automatically picks up the new palette.

This pattern is underused in most CSS architectures. Custom properties are typically used for global tokens (spacing, font sizes, breakpoints) rather than scoped context variables. The LCARS design made it obvious — if every panel variant has a unique color, you need a cheap way to express that color relationship across a subtree of elements without rewriting rules.

## Monospaced labels as information density

One choice I keep defending: the labels on panels and index entries use monospaced uppercase text with wide letter-spacing.

The accessibility case against this is real — it's harder to read than proportional lowercase text at small sizes. I've tried to mitigate it by keeping the labels short (they're labels, not sentences) and using them only where they communicate type information rather than prose content.

The reason it works visually: monospaced uppercase labels signal metadata. They read differently from body text. When your eye hits `DESIGN NOTES · 2026.04.18`, it processes it as a timestamp and category rather than something to read carefully. That's exactly the right cognitive mode for that information.

## What the aesthetic costs you

Leaning on a distinctive visual reference has a cost I should be honest about: it makes the design harder to judge on its own terms.

Some people will see "oh, this is the Star Trek thing" and stop there. They'll evaluate the reference rather than the execution. That's a real risk with any strong visual identity — the concept can swamp the craft.

The mitigation I've landed on: make the underlying structure excellent enough that the aesthetic feels earned rather than applied. If the navigation is well-organized, if the type hierarchy is clear, if the content is genuinely good, the LCARS layer reads as intention rather than decoration. If any of those things fail, it reads as costume.

That's a higher bar than a neutral design would set. But a neutral design doesn't give you anything to clear.
