I've written React professionally for three years. I still like it. But there are things I believed about it — things the ecosystem strongly encouraged me to believe — that I've had to quietly discard. This is about those things.

## Everything doesn't need to be a component

The first thing I unlearned: **not every piece of UI is a component**. Early in my React career, I abstracted aggressively. If I saw a pattern used twice, I extracted it. If a section of JSX got longer than a screen, I split it. Components were the unit of good thinking.

The problem is that components have costs. They introduce indirection. They split context across files. They create APIs — props, required/optional, defaults — that have to be maintained and understood. And sometimes the abstraction isn't load-bearing; it's just tidiness.

Now I wait longer before extracting. I ask: is this component being reused, or just split for length? Is the split making the logic clearer, or just making it shorter in one file? Length isn't the enemy. Confusion is. Sometimes a 200-line component with all its logic in one place is easier to work with than five 40-line components linked by props.

## State doesn't want to live in React

The second thing: React state management is not the best home for most state. This sounds like a plug for a state library, but it isn't — it's more basic than that.

**The browser already has state.** The URL is state. The DOM is state. Form inputs are state. The network response is state. React came along and offered to manage all of it, and for a while we let it. Then we built applications where a URL change required updating fifteen `useState` calls, and we wondered why things were hard.

I've become much more conservative about what I put in React state. If it can live in a URL param, it lives in a URL param. If it can live in an uncontrolled input, it does. If it can be derived from something else at render time, it isn't state at all — it's a computation. Reducing React state reduces the surface area for bugs.

## useEffect is not the right tool for data fetching

This one took me the longest to internalize, and to be fair, the React team said it clearly in the docs for years before I believed them.

`useEffect` is for synchronizing with external systems. Data fetching *looks* like that — you're syncing with a server — but the shape of the problem is different. You need loading states, error states, caching, deduplication, refetching on focus, background updates. `useEffect` gives you none of that. You build it yourself, badly, and then a month later you find the race condition.

React Query (or SWR, or a server component, or any of the other proper tools) handles these concerns correctly. The lesson wasn't just "use better tools." It was: **I was using a hammer because I knew how to hold it, not because it was right for the job**.

## The mental model that helps

The thing that helped me most was understanding React as a view layer — not an application framework. It renders UI based on state. That's it. That's the job.

When I treat React as a view layer, the question "where does this logic live?" becomes clearer. If it's computation over data, it lives outside React. If it's server state, it lives in a query library. If it's URL state, it lives in the URL. React gets the UI parts. It turns out React is very good at UI parts. It becomes much easier to work with when you stop asking it to be everything else.
