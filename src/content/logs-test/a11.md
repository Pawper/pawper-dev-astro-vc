I used to write commit messages like receipts. "Add search component." "Fix padding bug." "Update styles." Accurate, useless. What I was documenting was the what, not the why, and the what is already in the diff.

The shift happened when I started treating commits as a record of reasoning rather than a record of changes. A commit message that says "Fix padding bug" tells you nothing you couldn't learn from reading the code. A commit message that says "Increase header padding to prevent overlap with sticky nav on scroll" tells you the constraint that made the change necessary.

## Branches as hypotheses

The other change was treating branches as hypotheses. A branch named `feature/search` is a file drawer. A branch named `experiment/ranked-results` is a question: does ranking improve the experience enough to be worth the complexity?

When you name it as a question, you also know how to close it. Either the experiment proves out and gets merged with a clear commit explaining what it proved, or it doesn't and gets closed with a note on why it didn't. Either way, the decision is documented.

## Commit granularity

The right commit size is one coherent unit of reasoning. Not one file. Not one feature. One thought.

A commit that touches four files is fine if those four files represent one decision. A commit that touches one file is too large if it represents three unrelated decisions. The test: can you describe this commit in one sentence that starts with a verb and explains why? If not, it's probably too big, or too vague, or both.

## The log as an artifact

Six months into this project, the git log is one of the most useful documents I have. Not because the commits are beautifully written — some of them aren't — but because the pattern of decisions is readable. I can trace why the architecture went the way it did. I can find the moment I changed my mind about something and see what made me change it.

That's worth a minute of careful commit message writing every time.
